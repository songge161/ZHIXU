# 数据与测试治理

## 1. 数据库使用原则

本项目本地验证阶段沿用现有线上数据库，但数据库结构和访问只能通过 `../homecc-javaapi` 管理。

- 所有结构变化必须是 HomeCC Java API 中新的 Flyway 迁移；禁止从本地客户端手工改生产表。
- 新功能使用独立的 `progress_*` 表，不改变或复制现有用户、计划和专注表的归属关系。
- 主站既有数据默认只读；需要跨模块写入时必须先单独设计接口、权限和回滚路径。
- 本项目不保存数据库连接信息、Token、模型密钥或线上账号。

## 2. 建议的初始数据模型

| 表 | 用途 |
| --- | --- |
| `progress_spaces` | 学习方向或长期项目 |
| `progress_goals` | 分层目标与可衡量指标 |
| `progress_plan_versions` | 不可变计划版本 |
| `progress_plan_items` | 计划中的里程碑与行动项 |
| `progress_checkins` | 真实执行、阻碍和反思 |
| `ai_plan_proposals` | AI 提案与校验状态 |
| `ai_action_audits` | 用户确认后的应用审计 |

每条数据必须可校验用户归属；可变聚合包含更新时间和乐观锁版本，计划快照与审计记录追加保存。计划项需要跨版本稳定 ID；完成状态、实际投入和成果记录与不可变计划快照分开，避免重排后丢失历史或重复累计。关联现有每日任务的外键先保持可空、单向。

上表是初步候选，具体 DDL 未定。后续需纳入层级节点、习惯规则与记录、成果指标、同步批次及删除标记。新模块的提案和审计表统一采用 `progress_*` 前缀，避免与其他 AI 业务混淆。同步协议不依赖数据库自增 ID，使用稳定的外部 ID、基础修订号与幂等批次号。

## 3. 测试数据隔离与清理

使用线上数据库不等于允许留下无法区分的测试痕迹。实现数据表时应预留以下机制：

- 本地联调创建的数据带 `test_run_id`；该字段在测试阶段必填，用于一次性定位本轮全部测试记录。
- 新模块的查询接口默认排除测试数据；只有本地开发环境在显式传入当前 `test_run_id` 时才可读取。
- 读取主站数据时只读，不为测试向既有主站表写入模拟记录。
- 如确需写入既有能力，使用专门测试账号和可识别标记，并在同一验收任务中清理。
- 任何测试数据清理都先按 `test_run_id` 生成待删除数量和范围，再执行；清理后复查相关表无遗留记录。
- `test_run_id` 必须同时受当前用户、服务端测试权限与模块范围约束，不能仅凭客户端传入的批次号访问或删除数据。
- 本地原始资料和个人真实学习内容不会因为位于开发目录而自动变成测试数据；测试批次、测试附件和模拟数据必须单独标记。

## 4. 转线上前的默认收尾

除非另有明确要求，从本地验证转为线上版本前必须完成：

1. 按已登记测试批次清理本模块的测试数据及其关联审计、提案和专属测试附件；保留不含私人内容的数量与清理结果记录。不能全库匹配或删除真实资料、共享附件、主站数据。清理结果同步到本地副本并封存批次，避免旧文件再次上传测试数据。
2. 清除开发页面中的示例目标、Mock 数据、调试开关和测试入口。
3. 删除本地调试用的 CORS 放行、临时账号和开发环境变量。
4. 确认生产构建不包含测试数据、密钥、调试日志或开发 API 地址。
5. 使用正式账号完成最小回归，并记录清理与验证结果。

## 5. 当前限制

本项目尚未创建任何表、测试数据或数据库连接配置。本文件定义后续实现的约束，不代表已经具备隔离或清理能力。
