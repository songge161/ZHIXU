# 双端同步与容量控制提案

## 1. 状态与原则

用户强调本地与线上双端同步是核心，需要控制数据增长。本文件为方案提议，尚未实现或执行清理策略。

采用“结构化数据增量同步、资料文件按需同步、短期过程可压缩、正式成果可追溯”的设计。个人使用阶段先用 HomeCC API、现有 MySQL 与附件存储，不引入消息队列、独立搜索集群或实时协作算法。

本地工作区是可以离线整理的实际文件夹；浏览器缓存是第三份可重建副本，不是唯一原件或备份。云端保存已接受的共同版本，本地可以保存未提交草稿；用户可以从任一端编辑，最终经统一版本校验汇合。

存储容量与模型上下文预算分别治理；阶段摘要、按需检索及标准/高/最高模式见 [阶段摘要与上下文质量模式](./10-阶段摘要与上下文质量模式.md)。文件压缩本身不减少模型解读内容所需的上下文。

## 2. 按数据类型决定同步策略

| 数据 | 建议默认行为 | 控制增长的方法 |
| --- | --- | --- |
| 目标、任务、习惯、打卡 | 双端同步 | 只传变动记录，稳定 ID，不重复建任务 |
| 选定评估、目标标准、成果 | 双端同步 | 引用材料 ID 和固定版本，不在每份报告复制全文 |
| 讨论 | 同步确认的决定、接续摘要与草稿 | 原始长聊天默认保留在来源端，按需选入 |
| PDF、图片、论文原件 | 本地优先，用户选择云端保存 | 同账号按内容哈希去重，按需下载，不塞进同步 JSON 或 MySQL 大字段 |
| 提取文本、预览、检索缓存 | 按需生成 | 按原件哈希及处理器版本复用，可重建缓存设容量上限 |
| 临时同步日志、自动草稿 | 有限保留 | 合并未发出的重复草稿修改，保留关键节点和用户固定版本 |

完整历史无法同时做到无限保留和空间不增长。重要成果按用户意愿保留；对低价值过程做有界保留，对原件和总容量提供占用统计与限额。达到限额时暂停新增大文件或缓存并提示处理，不自动删除唯一资料或未同步改动。

## 3. 一次同步的流程

1. 本地确认修改写入待发送队列，并保存其基础版本；文件监听发现的 AI 输出默认只是提案草稿。
2. 联网后拉取上次游标之后的已提交变动，在固定的服务端同步水位内分页，保留本地待发送内容。
3. 对过时修改先检测冲突。首期空间版本冲突可直接提示重新整理，后续再引入逐记录、逐字段合并。
4. 发送变更批次：稳定记录 ID、基础修订号、唯一操作号、批次有效范围；每批限定记录数和字节数，附件单独传输。
5. 后端在同一事务中校验权限、写入业务数据、记录幂等结果与同步变更，再返回已接受版本；同空间提交顺序需串行化或具有明确的提交水位，不能把可能乱序提交的普通自增 ID 直接当可靠游标。
6. 本地收到确认后才移除待发送项，再拉取并落盘服务端结果。响应丢失时以原操作号重试，返回原结果，不重复创建。

自动同步只传输用户已经确认的编辑或提案草稿，不替用户批准 AI 的计划修改。无网时继续保存本地修改；恢复网络自动重试并显示状态。文件夹助手关闭时不承诺后台实时同步，用户仍可显式导入导出。

普通手工编辑可在保存后合并一小段时间再同步，窗口聚焦、联网恢复和手动“同步”也可触发；禁止每输入一个字符就写云端历史。首期无需持续高频轮询或实时广播。

## 4. 冲突的用户表现

例如本地把论文截止日改到周五，网站改到周日：显示两个值和共同旧值，让用户选一个或重新填写，不按电脑时间静默覆盖。不同记录上的独立改动可安全分别提交；关联目标删除、父子移动和约束变化仍做整体校验。

完成记录使用独立 ID，任务改名或重排不会新造一次完成记录。重复确认一个习惯周期也应有业务唯一约束。同步中的导出文件、下载结果不能再被监听器当成用户新编辑而来回上传。

界面只需展示：已同步、待同步数量、离线、存在冲突、附件仅本地，以及最近成功时间；大文件上传失败不应阻止小型计划记录同步。报告引用未上传原件时保留“仅本地”标记。

## 5. 防止历史无限复制

- 当前状态保存一份；自动草稿只保留有限检查点，关键计划确认和正式总评保留可追溯版本。
- 计划历史可用“关键快照 + 中间差异”，而不是每次保存复制全部目标、文件和历史。压缩前生成并验证新的基准，不能删除仍被保留报告引用的版本。
- 已同步且无冲突的操作队列可清理，未同步内容不能因队列满或过期被抛弃。
- 浏览器只缓存近期与用户固定离线的空间，旧附件按需下载；缓存清理不等于删除服务端内容。
- 文件去重限定在有权限的账号范围；修改后的文件是新版本，同文件多处引用仍为同一份对象。首期使用整文件上传和哈希去重，暂不做复杂的二进制差分。
- 云端原件使用现有附件存储能力，数据库只存归属、哈希、大小、存储键和引用；不能直接假定当前上传服务已支持这些能力，接入前需核实。

## 6. 有界同步日志与旧设备恢复

可配置同步日志保留窗口与最低支持游标。超过窗口的设备先保全本地未提交草稿，再下载所选空间当前快照，重新校验或生成提案；不从最初逐条重放所有历史。

删除使用显式标记，并在支持的离线窗口内保留。压缩日志和删除标记后，通过同步代次、过期游标或批次有效期拒绝旧请求，旧端必须重新建立基准；不能让旧副本把已删除或已清理的测试数据重新上传。幂等结果的保留期必须覆盖批次可接受期；过期重试不能被当作新请求执行。

附件删除先检查所有有效引用，再经过可配置回收期清理无引用对象；不能因一篇报告删除而删掉另一篇报告仍使用的文件。测试清理须同时封存批次并处理本地待发送队列。

## 7. 建议的初始保护参数

以下仅为待测起点，不是已确认的保留承诺：每批最多 200 条结构化变更且不超过 1 MiB；自动草稿每空间最多 50 个检查点；同步增量日志可先按 90 天评估。正式报告、固定版本和原始材料不套用草稿清理规则。

实现前根据样本体积调整，并显示附件、报告、缓存、历史分别占用多少空间。服务端对批次、单文件、账号总容量和同步请求速率均设限；提取文本也限制长度、页数及并发。容量达到阈值时先处理可重建缓存及临时数据，任何历史裁剪遵循已确认保留策略。

## 8. 同步不等于备份

误删也可能同步到另一端，因此还需要独立、带保留周期的数据库和附件备份以及可恢复导出。沿用现有备份能力前核实覆盖范围和恢复流程，不能把现有数据库备份当作附件也已备份。备份数量同样设上限，测试数据清理后不能由恢复流程直接带回在线业务。

## 9. 落地顺序与验证

先完成标准导入导出与双向往返，再做本地助手的一键拉取/推送和断网队列，最后自动触发。单纯手动导入不能宣称已经完成双端自动同步。

必须验证：断网重连、提交成功但回复丢失、重复包、重复文件、两端同时改同一字段、长期离线后恢复、删除后旧包重放、测试批次清理后回流、进程中断时本地落盘完整性、账号切换隔离及到达容量上限时不丢未同步数据。使用测试批次做容量和同步演练，不对主站真实数据施压。

## 10. 技术依据

- [RFC 9110 条件请求](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)：HTTP `If-Match` 可以用于提交前版本校验，防止并发覆盖；完整批次仍需业务事务、幂等与关联约束。
- [MDN 存储配额与清理](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)：浏览器存储受配额和清理机制影响，因此不能把浏览器缓存当作唯一可靠副本。
