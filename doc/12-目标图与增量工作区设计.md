# 目标图与增量工作区设计

更新时间：2026-10-14。本设计取代“每台设备生成标识”和“将全部数据写入一个 JSON”的方向。用户手动选择工作区目录；数据身份来自记录自身的稳定 ID，与 Mac、Windows 或浏览器无关。

当前已落地第一版目标树：`Space.parentId` 保存主要父节点，`Space.kind` 区分方向、计划、阶段、项目和分支；`Space.weight`、`Space.difficulty` 与行动对应字段用于加权评估。`graph/edges.tsv` 同时写入 `contains` 和行动的 `belongs_to` 边。行动记录包含可编辑的 `summary`，可由界面直接填写或从 Markdown/TXT 导入。AI 使用 `buildAiWorkspace` 生成按档位截断的工作区视图，标准、高、最高分别增加总结、资料和历史记录的数量与长度；行动保留稳定 ID 和标题供提案引用，但完整总结优先保留未完成行动和最近记录。完整工作区仍只留在本地状态和目录中，不会原样发送给模型。

## 1. 设计原则

1. 人和 AI 都能直接阅读：主要记录使用 Markdown，少量索引使用 TSV。
2. 一条事实只保存一次：界面统计、进度条、关系图和摘要属于派生结果，可从记录重建。
3. 稳定 ID 不跟标题、路径或设备变化：重命名和移动不产生新目标。
4. 写入按记录增量完成：SHA-256 相同的文件不重复写；`_index.tsv` 最后提交，作为当前有效记录集合。
5. AI 只提出变更：读取目录后生成可审查的新增、修改、连接或归档操作，用户确认后应用。
6. 进度保留依据：完成行动、达到里程碑、能力证据和目标清晰度分别计算，不混成一个虚假精确数字。

## 2. 当前目录协议

```text
workspace.md                 # 给人和 AI 的入口说明
_index.tsv                   # 当前有效记录及内容哈希，最后写入
goals/<goal-id>.md           # 方向、目标与里程碑
actions/<action-id>.md       # 可执行行动
evidence/<evidence-id>.md    # 成果、自述和资料摘录
drafts/<draft-id>.md         # 尚未采纳的讨论内容
reviews/<review-id>.md       # 阶段回顾
graph/edges.tsv              # 关系索引，目前先记录 belongs_to
```

每个 Markdown 文件使用受限的 YAML 风格元数据区。值采用明确的字符串、数字或布尔值，正文保留自然语言。索引保存 `kind、id、path、sha256`。读取时重新计算哈希：一致表示应用上次写入的版本；不一致表示用户或本地 AI 修改过，解析和校验成功后在预览中列出，不能静默覆盖，也不能仅因哈希变化而拒绝合法编辑。

删除记录时先从索引移除，旧文件暂时成为未引用文件，不参与计算；显式执行“整理目录”时再移到可恢复的归档区。这样中断写入不会使半套文件成为当前状态，也避免自动永久删除用户资料。

## 3. 目标图模型

整体不是一棵无限嵌套的任务树，而是“一个归属树 + 多种关系边”的属性图：

| 节点 | 作用 | 关键字段 |
| --- | --- | --- |
| Goal | 长期方向、阶段目标、项目或里程碑 | `id、kind、title、definitionOfDone、status、weight` |
| Action | 可安排和完成的最小行动 | `goalId、schedule、estimate、result` |
| Evidence | 作品、测试、自述、文件摘录 | `source、observedAt、reliability、contentHash` |
| Assessment | 一次有范围和依据的判断 | `scope、rubricVersion、dimensions、confidence` |
| Decision | AI 建议及用户的采纳结果 | `proposal、acceptedChanges、reason` |
| Summary | 给后续 AI 使用的阶段压缩 | `scope、sourceHashes、tokenEstimate、supersedes` |

边分为不同语义：

- `contains`：唯一的主要归属，形成树，用于导航和避免汇总重复计数。
- `depends_on`：先后依赖，必须组成有向无环图；写入前用 DFS 或 Kahn 拓扑排序检测环。
- `supports` / `contradicts`：证据支持或质疑目标、能力判断。
- `derived_from`：摘要、评估或 AI 提案来自哪些记录。
- `related_to`：不影响进度的弱关联，可以成环。

一个节点只能有一个主要父节点，但可以通过关系边关联多个方向。例如论文项目主要归属于“研究生阶段”，同时与“英语学术表达”建立 `related_to`，避免复制论文并在两边重复累计进度。

## 4. 进度算法

界面至少分开显示三件事：

1. 执行进度：已完成行动或里程碑的加权比例。当前原型的首版口径是：直接行动执行占 60%，下级节点按分量汇总占 40%；节点类型和难度再通过递减曲线修正显示分数。
2. 证据覆盖：有多少完成判断得到了成果、测评或可回查记录支持。
3. 目标清晰度：完成标准、期限、约束、当前基线和下一步是否明确。

里程碑执行进度可按下式计算：

```text
execution = Σ(weight_i × completion_i) / Σ(weight_i)
```

`completion_i` 由明确状态映射，例如未开始 0、部分验收 0.5、已验收 1；不能直接用子任务数量代替权重。父目标只汇总直接子里程碑，不递归重复累计所有后代。没有里程碑时显示“尚未定义衡量方式”，而不是 0%。

原型的首版加权执行口径如下。行动有效分量为 `actionWeight × (1 + 0.15 × (difficulty - 1))`；直接行动完成率记为 `direct`，下级节点按各自 `weight` 归一化得到 `children`。节点同时存在两者时：

```text
raw = 0.60 × direct + 0.40 × children
score = 100 × raw ^ gamma
```

只有直接行动或只有下级节点时使用存在的一项。`gamma` 随节点类型和难度增加：方向 1.22、计划 1.15、阶段 1.08、项目 1.04、分支 1.00，再叠加 `0.03 × (difficulty - 1)`。这样 60% 的行动执行是基础，上层目标和难度越高，新增同样的简单行动带来的分数越小；分量只影响同一父节点下的贡献，不会改变行动本身的完成事实。

每个完成值同时带 `confidence` 和证据引用。证据覆盖可以计算 `Σ(weight_i × evidenceConfidence_i) / Σ(weight_i)`，但界面应展示“依据充分 / 有部分依据 / 待验证”，避免把主观系数包装成精密测量。考试和记忆类学习可以在未来引入知识追踪或间隔重复模型；论文、研究能力等开放目标仍使用版本化量规和成果证据，不能共用一套所谓掌握度算法。

目标扩展时不回写历史百分比。每次重要范围变化生成 `scopeVersion`，保存旧分母和变更原因，同时展示“按当前范围”和“上次评估时”的结果，避免 AI 新增任务后让已有努力看起来突然归零。

## 5. 计划排序

行动必须先通过约束过滤：依赖已满足、未暂停、可用时间足够、截止日和用户锁定项不冲突。候选行动再按可解释分数排序：

```text
priority = urgency + impact + readiness + continuity - effortRisk - contextSwitchCost
```

首期使用规则化权重并显示排序理由；数据积累后才能根据实际耗时误差调整估计。复杂日程可进一步使用约束规划或整数规划，但不能在数据不足时假装已经找到全局最优安排。

## 6. 本地修改、同步与冲突

当前原型通过索引哈希识别目录外部变化，并在整体读入前预览。下一阶段把变化表达为操作：

```text
changeId, recordId, baseHash, operation, patch, createdAt
```

云端只上传发生变化的记录和关系。服务器用 `baseHash` 判断是否存在并发修改：一侧未变化可快进；不同字段可做三方合并；同字段冲突则保留双方版本并请求用户选择。操作具有 `changeId`，重复提交保持幂等。同步游标属于会话，不需要永久设备指纹。

附件使用内容寻址：计算 SHA-256 后保存在 `blobs/<hash>`，多处引用同一文件不会重复保存。Markdown 只保存附件引用和摘录。SQLite、全文索引或向量索引可以作为大型工作区的本地派生缓存，但不是唯一权威源；损坏后应能由 Markdown、TSV 和附件重新构建。

## 7. AI 上下文与阶段压缩

询问某个目标时，从该节点出发读取有限图邻域：祖先路径、直接子目标、未完成行动、最近相关证据、未解决冲突和最近阶段摘要。按主题相关性、时间、证据质量和用户固定项排序，在 token 预算内选择；不是简单读取整个目录。

摘要保存其来源文件哈希。任何来源变化都会使摘要变为 `stale`，需要重新生成或局部修补。高档模式扩大图邻域并增加证据交叉核验，最高档再检查矛盾和历史版本；它们不能只用“多塞一些全文”来实现。

## 8. 实施顺序

1. 稳定当前多文件目录协议、外部修改预览和增量写入。
2. 将 Goal 扩展为带 `parentId、kind、definitionOfDone、weight、scopeVersion` 的层级节点。
3. 扩展 `graph/edges.tsv`，实现环检测、拓扑排序和关系视图。
4. 建立里程碑验收、证据关联及多维进度，不再将任务勾选率作为总目标进度。
5. 定义 AI 变更操作和部分采纳界面，再让本地 AI 生成变更包。
6. 增加内容寻址附件、派生索引、三方合并与云端增量同步。

当前代码已实现第 1 步的基础，并完成第 2 步的首版：按记录写 Markdown、哈希跳过未变化记录、索引最后提交、关系表、目录外部修改检测和读取前预览；Goal 已支持 `parentId` 和 `kind`，行动支持总结正文。通用图算法、证据权重和冲突合并仍是明确的后续工作，不能当作已经完成。
